# REA capability audit — VS Code 0.3.3 / Engine 6.7.0

Audit date: 2026-10-20. Scope: current working tree, including pre-existing uncommitted changes; this is not a verification of the packaged VSIX. Only this document was created for the audit. No engine, extension code, MCP configuration, installed paths, package, commit or publication was changed.

## Resumen ejecutivo

El catálogo MCP real contiene **207 herramientas de múltiples dominios**. El flujo web automático utiliza como máximo **cuatro (1,93 % del catálogo total)**; este porcentaje mide integración, no calidad ni cobertura del navegador. Codex y la invocación manual ya tienen acceso al catálogo completo, sujeto a autorización y requisitos del proveedor.

La mayor oportunidad consiste en añadir observación de sesiones, comparación de capturas, descubrimiento WebMCP y escenarios controlados con presupuestos explícitos. Para JavaScript, REA ofrece una alternativa más controlable: exportar evidencia ya capturada y analizar archivos locales seleccionados con límites de heap, tiempo y nodos. La adquisición inicial de fuentes sigue siendo un riesgo independiente; no debe usarse esta ruta para eludir los límites actuales.

REA no expone estilos calculados ni geometría por elemento en las herramientas inspeccionadas. Tampoco garantiza reconstrucción completa ni equivalencia funcional. Se recomienda mantener el flujo pasivo como base, añadir capacidades por etapas y aislar el trabajo pesado. Las herramientas anunciadas, las pruebas con fixtures y los resultados reales deben comunicarse por separado.

## Current integration coverage

| Surface | Actual coverage | Limits / evidence |
| --- | --- | --- |
| Automatic web analysis | `list_browser_targets` → `inspect_web_page` → optional `capture_web_screenshot` → budget-admitted `analyze_web_bundle` | Sequential, exact single page URL and origin; no crawling or interaction. Screenshot is attempted before bundle admission. |
| Browser ownership | Sidebar launches an isolated browser through `startAnalysisBrowser`; companion MCP exposes `acquire_browser` and `release_browser` | Browser launch/navigation to initial URL is extension behavior, not evidence that passive REA tools navigate. Companion is a separate server. |
| Explorer query editor | `list_unknowns` only | Five-field reviewed schema; local pagination defaults offset 0 / limit 50, maximum 100. |
| Generic manual command/client | Any live catalog name with complete JSON object arguments | Explicit authorization; schema validation remains with REA. Full result blocks/metadata preserved. Dispatchability does not establish backend operability. |
| Native VS Code MCP / Codex MCP | Full engine catalog, not the automatic four-tool allowlist | Separate processes/sessions and host approvals; retained IDs cannot be shared implicitly. Existing configuration was read only. |
| TaskOrchestrator | Regex recommendations and sequential caller-defined steps | No autonomous scenario planner or reconstruction pipeline; stops on `isError`, no mutation retry. |
| Reconstruction project | Original static HTML/CSS, disabled placeholder controls, brief, sanitized evidence projection and verified viewport PNG | Does not invoke REA reconstruction verification, recreate original CSS, implement API contracts or prove parity. |

Automatic page capture enables accessibility text and observes **500 ms**. Console text, JSON body shapes, WebSocket shapes, storage keys/fingerprints are disabled; script sources are enabled only for bundle analysis. Source-map fetching is disabled. Thus DOM/AX, resource URLs, script metadata, URL declarations and attach-window network metadata are integrated, while many optional facets are unused even within `inspect_web_page`.

Local projections cap DOM processing at 5,000 nodes, AX scanning at 80 nodes, DOM URLs at 35, resources/network requests at 25 each, static routes/endpoints at 15 each, fingerprints at 15 and findings generally at 240. These are display/report limits after REA allocation. The report links Evidence IDs and digests but does not export a complete canonical REA evidence bundle.

Default request deadlines: 60 seconds for web inspection/screenshot/discovery and 300 seconds for bundle analysis. Cancellation/timeout does not intentionally disconnect MCP. Engine process death remains a distinct failure; retaining a connection after a rejected bundle does not demonstrate parser memory safety.

## Safer alternatives and memory boundaries

1. **Metadata-first capture:** DOM/AX/resource/script metadata, screenshot, WebMCP declaration inventory and bounded-duration session observation can answer useful questions without building a full JavaScript AST. More time observing improves event opportunity, not completeness. Duration limits do not strictly bound source, DOM or event memory.
2. **Budgeted scenarios:** `capture_browser_scenario` exposes event/allocation, transaction, body and header retention budgets under `capture.limits`; request/response bodies and header values are independently opt-in. Actions include `goto`, `click`, `fill`, `press`, `select_option`, `check`, `uncheck`, `wait_for`, and `wait_for_timeout`. Set per-action deadlines where supported; omitted deadlines can wait until completion/cancellation. Budgets bound measured retention, not total Chromium/REA RSS or every transient allocation. Scenario capture executes the application and needs action-specific authorization.
3. **Offline selected-source analysis:** `export_web_scripts` accepts a saved capture and exports only source bytes already retained, with digests and a manifest; it does not refetch. `analyze_javascript_application` then accepts exact `source_paths` (no globs or implicit dependencies), `max_heap_mb` (128–16,384 MiB; default 1,024), per-source `analysis_timeout_ms` (default 300,000), and aggregate/per-file semantic node and unknown budgets (defaults 100,000/20,000). It isolates source analysis; these controls do not apply to `analyze_web_bundle`. Heap is V8 old-space, not a total RSS ceiling; Bun has platform-specific enforcement caveats in the contract. Inventory and parent result retention still cost memory. Test with conservative explicit values and exact selected inventory paths before enabling automatically.
4. **Targeted source evidence:** event-listener inspection can reveal direct handler ownership without dispatching events, but it returns exact script text and may still be expensive; delegated listeners remain unknown. `observe_web_execution` returns coverage plus hashed source text, changes target execution behavior and is not a cheap metadata-only fallback. Neither is a blanket safe substitute for oversized source admission.
5. **Offline bounded source-map/import probes:** `trace_web_source_location` uses an independent 192 MiB old-generation worker and 20-second deadline, limits a map to 4 MiB and reply to 32 MiB, and does not fetch/execute application code. It requires an explicitly paired local map and cannot authenticate that pairing by itself. `trace_web_module_imports` verifies a selected script/manifest and has 32 MiB manifest, 16 MiB source, 4 MiB import-map and 20-second native deadline limits; native literal resolution runs a trusted resolver stub in owned Chromium, with requests fulfilled/blocked, not captured application code. Computed/bundler imports remain unknown.
6. **Summary plus retained views:** application/artifact/network/WASM summary detail and `get_evidence_bundle(detail: 'summary')` reduce transfer and duplicate decoding. `inspect_analysis_view` pages retained data, including a HAR-derived API surface. **Summary is not a parser memory limit**. `inspect_web_network_capture(record_ordinals)` still decodes every record before selection; malformed/oversized captures fail without partial success.

The current automatic admission remains appropriate: complete script inventory, at most **100 scripts**, **500,000 characters per script**, **2,000,000 total characters**, all sizes known. These are conservative source-character thresholds, not bytes or empirically established safe heap limits. The web bundle contract has no source selection, heap/AST budget or summary mode. `include_script_sources: false` does not establish a usable safe static-analysis route. Disabling maps reduces extra work but leaves parsing costs.

There is a time-of-check/time-of-use race: `analyze_web_bundle` captures again after the admission inventory. New or changed scripts can evade the earlier size estimate. The 64 MiB MCP transport buffer caps encoded buffering, not engine heap, decoded JSON, ASTs or RSS. Display caps operate too late to protect the engine. The earlier Excalidraw failure mechanism is not conclusively established by its summarized stderr; do not claim a proven leak or a full memory fix.

**Acquisition is a separate gate:** export requires sources in the saved capture (or scenario response bodies). Current automatic inspection deliberately does not retain sources. Fetching all scripts just to select a few afterwards can recreate the original memory pressure. Never capture oversized sources as a fallback after the admission rejection. Use previously authorized bounded captures/local files, or leave source analysis unknown. Offline worker isolation does not retroactively bound initial capture/export or parent inventory.

## Recommended architecture and prioritized roadmap

Use a staged capability planner around the unchanged engine: live contract/provider check → metadata capture → admission → optional scoped probe → artifact/coverage store → reconstruction brief. Give each stage its own authorization scope, cancellation, deadline, declared input/output budgets and explicit partial/unavailable outcome. Run one expensive job at a time. Persist artifact identity and coverage rather than repeatedly copying complete source/evidence into UI state.

For operational isolation, a future extension implementation can schedule heavyweight authorized analysis in a separate client-owned REA process launched from the **existing configured executable/path**, with its own session lifecycle. Keep interactive capture results outside that worker, export/import portable evidence deliberately, and terminate only owned resources. This is a proposed extension design, not an engine memory guarantee or a request to change MCP configuration. Enforced OS memory limits require platform-specific implementation and validation; do not assume a request timeout kills all work or bounds RSS.
